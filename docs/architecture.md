# Architecture

How Scry is built: its layers, what each may lean on, how a failure goes, and how each part keeps and lets go of what it holds. Read this first before changing code.

Code: `src/Core/Guard.cs`, `src/Core/Faults.cs`, `src/Core/Kept.cs`, `src/Model/Learned.cs`, `src/Model/Steps.cs`, `src/Core/Log.cs`, `src/Core/Settings.cs`, `src/Core/About.cs`.

See also: [standards](standards.md), [selftest](operations/selftest.md), [index](index.md); all notes in [the index](index.md).

## Layout of the code

Scry is built in layers, each leaning only on those below it, which a test holds by reading every name in the source with the compiler (`LayerStandardTests`). `src/Model` holds everything that needs no game: kinds, search and suggestions, the list's groups, the rules for preview copies, adjustments, looks and outfits, favourites and history, links, leftovers, place names, location rules, example dungeon layouts, the stage's framing and the startup check's fingerprints; its tests are the model's own, while the standards tests read the whole source and the self-test. `src/Core` holds what every layer leans on: the one way failures are handled (`Guard`, `Faults`), the log (`Log`), the settings (`Settings`), Scry's id and version (`About`), timing, what Scry makes (`Kept`) and the self-test's host. `src/Catalog` reads the game into the model, the fact readers among it (`src/Catalog/Facts`), and `src/Patches` watches the game: the few Harmony patches and the startup check. `src/Preview` makes and plays the copies; `src/UI` draws the panel and keeps the game's input off while it is open. At the top of `src`, the plugin, the session and the command put them together: the plugin gives the layers below the log and the settings and connects what they tell (`Timing.FrameDone` to the monitor, `ScryPanel.CloseAsked` to the session), and the session reads the world's catalog, opens and closes the panel and hands it the world's explorer each frame. What reads the world and makes the previews never calls the panel, but says when an entry's details change (`Learned`: a place's contents read, a dungeon's rooms read, every location read), and the details kept for the panel listen. Entries are found by their key through the world's catalog (`WorldCatalog`, an `EntryCatalog` the explorer shows too), not by going through it.

## How the code is written

A rule or a wording goes in the model, with tests named for what a player needs and checked by mutating the code under them; what needs the game reads the prefab into plain figures and hands them over (`SourceFacts`, `PartTraits`, `PrefabShape`, `SpawnFacts`), and the model decides and words them (`SourceWords`, `PlaceParts.RoleOf`, `ContentOrder`, the `...Words` classes). Every phrase a player reads is worded once, in the model, by a `...Words` class, and tested there: the panel's by `PanelWords`, `ListWords`, `DetailWords` and `StageWords` among others, the catalog's by `CatalogWords`, `SpawnWords` and their kin, the console's, the monitor's and the startup check's by `ConsoleWords`, `MonitorWords` and `OffWords`. The rest of Scry, the fact readers (`src/Catalog/Facts`) and the panel alike, hands the model plain values and shows what comes back, putting no text together itself beyond a fixed label or value, as a test holds (`WordingStandardTests`). Text no player reads as Scry's wording is put together where it is used: a line for the log or a failure report, the name of a guarded or timed part, a key or an id, a Unity object's name, and anything in a member marked `[Diagnostic]`, which is for whoever looks after Scry (the self-test's strip, the console's dump, the catalog's timings). The links a value carries that play music or copy a website rather than going to an entry are made and read in `EntryKeys`. A rule only the game can run, or a bug found in game, is moved into the model before it is changed, so the change has a test. Where a detail follows one of the game's rules, its comment names the game's method, and the startup check watches that method; a test fails for a game method a comment names that is neither watched nor patched nor called, and for a game member reached by its name that the check does not look for.

A failure goes one way. `Steps.Run` is the one place any failure is caught, and Scry's work runs through it by `Guard`, by how much a failure costs: `Guard.Run` for a part of the work, told once and stopping nothing after it, timed under a name where it is a part of the frame; `Guard.Each` for one item of many, a prefab read or shown, which leaves only that item's part out, counted and summed up; `Guard.Read` for a step of reading the catalog; each with a form that works out a value and says whether it did. The model, which knows no game, runs its own through `Steps.Run`. What fails is told through `Faults`, which the self-test counts; only a failure of a named kind a parser or the runtime gives on purpose is caught where it comes. A standards test holds every catch and every failure written to the log to this. What is kept of a world registers how it is forgotten (`WorldCaches`), and a test over the source fails for a store that is never emptied. What one feature keeps lives in an object of its own that lets go of it itself (`BiomeGround`, `StageCreatures`, `StageExample`, `FloorCut`, `SearchAssist`); a panel part's few fields stay in its own file, named for it, until it holds a cache or a job, and then it becomes such an object.

The panel, the stage, the previews and what is known of the world are each one static class in parts, a file for each part: each part keeps its own state and lets go of it itself (`ForgetList`, `ForgetClips`, `ForgetSpawns`), and another part reads it but changes it only by asking, through a method named for what it does (`StartDrag`, `ShowCard`, `TurnTo`, `UndoStarted`), as a test holds (`OwnerStandardTests`); what a class lets others set is a property. Lower layers never call the panel (`Learned`), which a test over the source holds to, as it holds the reading of the game to the few preview helpers it shares, entries are found by key (`Explorer.Find`), what a play button started is asked after by the thing played or a `PlayKey`, never by text the previews and the panel would each spell, and a type's fields are looked through and read one way (`TypeFields`), an effect list's slots one way (`EffectSlots`: whatever plays a list or tells of it counts the slots the game plays, switched on with a prefab; only telling why a list showed nothing names the others), and a prefab or item by its name one way (`GamePrefabs`), which tests over the source hold to; a Unity object is held to be none by Unity's own check, which `?.` and `??` skip, so neither is used on one that has not gone through `OrNull()` first (`UnityNull`), as a test holds; and Scry's own timers keep unscaled time, running on while the game is paused, while what moves as the world moves (a fall, a projectile's flight, a windmill, the water) keeps the game's, as a test holds; and every texture, render texture or mesh Scry makes is noted with `Kept` as it is made, or destroyed where it was made to work with, as a test holds too.
