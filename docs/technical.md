# Technical notes

How Scry works, what it copies from the game, and what to do when the game updates. Scry runs only in the game client (`BepInProcess("valheim.exe")`); a dedicated server never loads it. Nothing it shows is networked or saved, so it needs nothing from the server and no other player sees it.

## Layout of the code

Scry is built in layers, each leaning only on those below it, which a test holds by reading every name in the source with the compiler (`LayerStandardTests`). `src/Model` holds everything that needs no game: kinds, search and suggestions, the list's groups, the rules for preview copies, adjustments, looks and outfits, favourites and history, links, leftovers, place names, location rules, example dungeon layouts, the stage's framing and the startup check's fingerprints; its tests are the model's own, while the standards tests read the whole source and the self-test. `src/Core` holds what every layer leans on: the one way failures are handled (`Guard`, `Faults`), the log (`Log`), the settings (`Settings`), Scry's id and version (`About`), timing, what Scry makes (`Kept`) and the self-test's host. `src/Catalog` reads the game into the model, the fact readers among it (`src/Catalog/Facts`), and `src/Patches` watches the game: the few Harmony patches and the startup check. `src/Preview` makes and plays the copies; `src/UI` draws the panel and keeps the game's input off while it is open. At the top of `src`, the plugin, the session and the command put them together: the plugin gives the layers below the log and the settings and connects what they tell (`Timing.FrameDone` to the monitor, `ScryPanel.CloseAsked` to the session), and the session reads the world's catalog, opens and closes the panel and hands it the world's explorer each frame. What reads the world and makes the previews never calls the panel, but says when an entry's details change (`Learned`: a place's contents read, a dungeon's rooms read, every location read), and the details kept for the panel listen. Entries are found by their key through the world's catalog (`WorldCatalog`, an `EntryCatalog` the explorer shows too), not by going through it.

## How the code is written

A rule or a wording goes in the model, with tests named for what a player needs and checked by mutating the code under them; what needs the game reads the prefab into plain figures and hands them over (`SourceFacts`, `PartTraits`, `PrefabShape`, `SpawnFacts`), and the model decides and words them (`SourceWords`, `PlaceParts.RoleOf`, `ContentOrder`, the `...Words` classes). Every phrase a player reads is worded once, in the model, by a `...Words` class, and tested there: the panel's by `PanelWords`, `ListWords`, `DetailWords` and `StageWords` among others, the catalog's by `CatalogWords`, `SpawnWords` and their kin, the console's, the monitor's and the startup check's by `ConsoleWords`, `MonitorWords` and `OffWords`. The rest of Scry, the fact readers (`src/Catalog/Facts`) and the panel alike, hands the model plain values and shows what comes back, putting no text together itself beyond a fixed label or value, as a test holds (`WordingStandardTests`). Text no player reads as Scry's wording is put together where it is used: a line for the log or a failure report, the name of a guarded or timed part, a key or an id, a Unity object's name, and anything in a member marked `[Diagnostic]`, which is for whoever looks after Scry (the self-test's strip, the console's dump, the catalog's timings). The links a value carries that play music or open a website rather than going to an entry are made and read in `EntryKeys`. A rule only the game can run, or a bug found in game, is moved into the model before it is changed, so the change has a test. Where a detail follows one of the game's rules, its comment names the game's method, and the startup check watches that method; a test fails for a game method a comment names that is neither watched nor patched nor called, and for a game member reached by its name that the check does not look for.

A failure goes one way. `Steps.Run` is the one place any failure is caught, and Scry's work runs through it by `Guard`, by how much a failure costs: `Guard.Run` for a part of the work, told once and stopping nothing after it, timed under a name where it is a part of the frame; `Guard.Each` for one item of many, a prefab read or shown, which leaves only that item's part out, counted and summed up; `Guard.Read` for a step of reading the catalog; each with a form that works out a value and says whether it did. The model, which knows no game, runs its own through `Steps.Run`. What fails is told through `Faults`, which the self-test counts; only a failure of a named kind a parser or the runtime gives on purpose is caught where it comes. A standards test holds every catch and every failure written to the log to this. What is kept of a world registers how it is forgotten (`WorldCaches`), and a test over the source fails for a store that is never emptied. What one feature keeps lives in an object of its own that lets go of it itself (`BiomeGround`, `StageCreatures`, `StageExample`, `FloorCut`, `SearchAssist`); a panel part's few fields stay in its own file, named for it, until it holds a cache or a job, and then it becomes such an object. The panel, the stage, the previews and what is known of the world are each one static class in parts, a file for each part: each part keeps its own state and lets go of it itself (`ForgetList`, `ForgetClips`, `ForgetSpawns`), and another part reads it but changes it only by asking, through a method named for what it does (`StartDrag`, `ShowCard`, `TurnTo`, `UndoStarted`), as a test holds (`OwnerStandardTests`); what a class lets others set is a property. Lower layers never call the panel (`Learned`), which a test over the source holds to, as it holds the reading of the game to the few preview helpers it shares, entries are found by key (`Explorer.Find`), what a play button started is asked after by the thing played or a `PlayKey`, never by text the previews and the panel would each spell, and a type's fields are looked through and read one way (`TypeFields`), an effect list's slots one way (`EffectSlots`: whatever plays a list or tells of it counts the slots the game plays, switched on with a prefab; only telling why a list showed nothing names the others), and a prefab or item by its name one way (`GamePrefabs`), which tests over the source hold to; a Unity object is held to be none by Unity's own check, which `?.` and `??` skip, so neither is used on one that has not gone through `OrNull()` first (`UnityNull`), as a test holds; and Scry's own timers keep unscaled time, running on while the game is paused, while what moves as the world moves (a fall, a projectile's flight, a windmill, the water) keeps the game's, as a test holds; and every texture, render texture or mesh Scry makes is noted with `Kept` as it is made, or destroyed where it was made to work with, as a test holds too.

Text is English whatever the PC is set to. Every number shown, in the panel and in the log, becomes text through `Numbers`, its thousands by commas, and comments and these notes write a thousand or more with commas too, as a test holds; what Scry writes into its own files and keys to read back, and every number it reads from text, goes through `Stored` (the panel's place in `PanelPlace`); a list reads through `Naming.Joined`, names with commas through `Naming.Commas`, a title with how many it holds through `Naming.Counted`, a multiplier ("×1.5") through `Numbers.Times` and a text begun with a capital through `Naming.Capital`, the last two as tests hold, and a tip's lines one under another through `Naming.Lines`; and string checks compare ordinally. The tests in `tests/Scry.Tests/Standards` compile the whole source and the self-test with the compiler's own types (`ScrySource`) and fail at each place a standard is not kept, implicit ones too, such as a count in an interpolated string. Comments and documents say what a part does and why, in the same plain words as the panel. The build fails for a comment that links to something gone or names parameters wrongly, a test fails for a doc comment over no member or two over one (`DocStandardTests`), and the build for any finding of the .NET code analysis rules, all of which run but the few `Analysis.globalconfig` turns off, each with its reason (`BuildChecks.props`, shared by Scry and the self-test); a test fails for a name in these notes, or a search example in the README, that the source no longer has. The panel lays out every row of chips, tabs, buttons and segments by one flow (`ChipFlow`), a long list ending in one chip for the rest, and every labelled row (a slider, segments, toggles) with its label in one column (`RowLabel`). Its colours are the skin's, each named once in `Skin` or made there from one (`Skin.Alpha`, `Skin.Shade`, `Skin.Lift`), and so are its text styles, made together and made again together when the panel's scale changes; a label in a colour of its own is drawn one way (`Skin.LabelIn`), and a test fails for a colour or a style the panel makes elsewhere. A test also fails for a character lost on the way (U+FFFD) in any of the repository's own files. Scry offers no API, so every type is internal but the plugin classes BepInEx loads, as a test holds. The self-test is a plugin of its own; what it reads from Scry is a view of real state or how often a part of the panel was drawn (`ScryPanel.Drawn`, counted on repaint), and where only a click opens a box, a small opener sets what the click would (`ShowHelp`, `OpenViewMenu`, `OpenSlider`); nothing else is added for it.

## The catalog

The catalog is read once per world, a few milliseconds each frame, starting ten seconds after the world is entered, so it is usually ready before the panel is first opened. Opened earlier, the panel says how far the reading has got, and the reading takes a bigger share of each frame while the panel waits. Nothing shows until all of it is read, since an entry's kind, links and groups are only known then.

It holds every prefab registered with the scene, every status effect in the object database, every raid the world has switched on, every location the world can place and every dungeon room it can build with, and every prefab reached through an effect list. Most sounds and many visual effects are never registered on their own: they hang off the effect lists of the items, attacks, pieces, creatures, status effects and interface that play them, so those lists are followed, including effects that point at further effects.

Leaving a world lets go of everything read of it. Each part of Scry that keeps something of a world registers how it forgets it (`WorldCaches`), and a test over Scry's own source fails when a store of world things is never emptied or its class never registers.

A prefab is the game's own when it was in the scene's lists before any mod ran, read by a first-priority prefix on `ZNetScene.Awake`, a status effect the same way on `ObjectDB.Awake`, a raid on `RandEventSystem.Awake` and `ZoneSystem.SetupLocations` (which adds the raids of the game's location lists), a location on `ZoneSystem.SetupLocations` and a room on `DungeonDB.SetupRooms`. An effect is the game's own when anything of the game plays it.

### Kinds and groups

An entry's kind comes from its components, what it does before how it looks: anything with a character is a creature, then projectiles, items and pieces. What is chopped, mined, picked or grown, or breaks into drops, is a resource. Something with only sound is a sound, particles or anything only ever played from an effect list are an effect, and the rest is other.

A mod that makes the game's own prefabs buildable (*MoreVanillaBuildPrefabs* adds a `Piece` to hundreds of them) does not change their kind. Such a mod leaves its `Piece` switched off on the prefab, which none of the game's own pieces is, so a ruin wall stays what the game made it and its facts say the mod makes it buildable. A crop planted with the cultivator is a piece, since it is built like one.

Each kind's tab groups its list by what the game itself says: items by their item type (weapons by the skill they train, armour by slot), pieces by the hammer's tabs and then by tool (a piece in several tools under the first, the hammer before the rest), creatures by faction, resources by how they are gathered, effects and sounds by the names of the effect lists that play them, projectiles by what fires them, and status effects by what gives them.

Raids are named by the message the game shows when they start and listed in three groups: the raids the game rolls for (by the raid roll or a timer of their own), then the bosses' fights, then what something else starts. A boss's fight is the event its `Character.m_bossEvent` names, which the game has on while the boss's health bar shows (`RandEventSystem.GetForcedEvent`, shown while the boss is alerted within `EnemyHud.m_maxShowDistanceBoss`), for its music and weather; it has no message, so it is named for its boss, its page goes to the boss and the boss's page to it, and Enter plays its music. A raid's or a fight's *Music* plays when clicked, as a place's does, and its *Weather* says what that weather does to whoever is out in it, as `EnvSetup` sets it: wet soaks you outside without a roof (`Player.UpdateEnvStatusEffects`), cold and freezing give their statuses by day or only at night, freezing outranking cold (`EnvMan.CalculateCold`, `CalculateFreezing`), some are always dark, and each blows within a range of wind (`WeatherWords`). Within a group they come in the order the bosses are fought: a fight by its boss's health, a raid by the health of the strongest boss whose defeat it waits for, those waiting for none first (`RaidGrouping`); boss health grows from Eikthyr to the Fader, so a mod's boss falls in place too.

Mods are listed by whether they add to the game, only hook into its drops or spawning, or neither, as far as Scry sees.

A build tool is any item with a build table (`m_buildPieces`): the hammer, the hoe, the cultivator and any mod's own. Every tool a piece is in is noted with the tab it is on there, named as the tool names it (`ToolBook`), so a piece says what builds it and on which tab, one tool as a link to it, several as chips, and a tool lists what it builds, a row for each of its tabs in its own order.

Locations are grouped by biome in the order players meet them, one placed in several biomes after those. A dungeon or camp and its rooms are one group of their own right after its biome's other places ("Black Forest · Burial Chambers"): the location first, tagged dungeon or camp with its prefab to tell its variants apart, then its rooms indented under it and tagged, entrances first, then rooms, then end caps, dividers and walls (`PlaceGrouping`, a rank within the group, `Entry.GroupRank`). A room has one home, the dungeon of its lowest theme flag (`Room.m_theme`), so a room two dungeons share (the Burial Chambers' and Hildir's crypt's) is under the first and names both. What kinds of room a dungeon is built of is in its location's bundle, so until a location building a theme is read (by selecting it, laying out its example, or reading every location) that theme's rooms wait together after every biome, under the theme's name.

What is no prefab is kept under a key of its own kind (`EntryKeys`: a status effect's "se:", a raid's "raid:", a location's or room's "loc:", a mod's "mod:", each with its name), so favourites, recent and links never mistake it for a prefab of the same name. Items only creatures carry, which nothing a player meets gives, go last under *Carried by creatures*.

## Search and keys

The search matches names and takes terms (`kind:`, `has:`, `biome:`, `mod:`, `playedby:`, `station:`, `in:`, `is:`, `weak:`, `resists:`, `immune:`, `damage:`, `skill:`, `drops:`, `from:`, `needs:`, `gives:` and `spawns:`), each value matched anywhere in what it names, spaces left out, but for the words `is:` and the fight terms take, matched by the start of the word or of any part of it; a name in quotes matches only what is called exactly that, by the game's name or the prefab's, ignoring case, and a quote not yet closed reads as plain words while it is typed; commas part a value into several, any of which may match (`biome:swamp,plains`), and after a comma the next value is suggested. A search that finds nothing at all is tried once more with each word no name holds read as the word of the catalog's names one slip away from it, a letter wrong, missing, extra or two swapped, or whose start is, for a word still being typed, words of three letters or fewer left alone (`SearchSlip`); where that finds anything, the list shows it under a note naming what was typed and what is shown. The search's help lists an example of each term beside what it finds (`SearchHelp.Lines`, every key named, as a test holds); a click on an example tries it in the search. In the list the part of each name a typed word matched is lit behind the text, each word where the search finds it first and a quoted name whole (`SearchLit`, `ScryPanel.Lit.cs`), measured where the row's style puts the letters. `is:` asks what a thing is in one word (`SearchFlags`), read into each entry once the catalog has every entry linked and grouped (`CatalogBuilder.Terms.cs`) as its details tell the same: a boss, tameable or flying creature by `Character.m_boss`, a `Tameable` and `Character.m_flying`; a wearable item, a weapon or ammo by its item type, food by its food values, craftable by an enabled recipe; a buildable piece by a tool that builds it; silent with nothing to see or hear, unsure where a mod was named by clues. The fight terms are read the same way (`SearchFight`): `weak:`, `resists:` and `immune:` from the cells of the resistance grid the details draw (a creature's, worn armour's while worn), so a creature's tool damage it takes none of, drawn quietly, is no immunity; `damage:` from the damage figures the details tell, a creature's from its attack items; `skill:` from the skill a weapon, ammo, shield or tool trains, as the details name it. The link terms follow what the details link, each linked thing named by the game's name or its prefab's (`Entry.TermLinks`): `from:` and `drops:` the lines an item's page tells where it comes from, by a creature's drops, a drop table or picking (not producers or traders); `needs:` its *Used in* rows that craft, upgrade, build or turn something into another; `gives:` what its page lists under *Given by*, a status effect's givers; `spawns:` a thing's *Spawns* links and the creatures a raid brings. Suggestions come from an index of every value each key can take, built on a worker thread once the catalog is read, each with how many entries it finds. The best one shows faint after the text; Tab takes it, and further presses cycle through the rest.

Enter takes a suggestion while one is offered for a word being typed. Otherwise it does the selection's main thing, as a double click does: a sound or effect plays, a projectile flies, a status effect shows on the person, a creature makes its first attack, a wearable item is put on or taken off, a location or room plays its music or stops it, a raid rolls its creatures anew, and a tree, log, rock or piece is felled or broken. In the clip and effect filters Enter plays the first match. Escape leaves a text box first and closes the panel the second time; Ctrl+F goes to the search.

IMGUI's text field uses up any key that types no character, so Enter is taken before the field is drawn. It leaves Tab alone, and an unused Tab moves Unity's keyboard focus on, so Tab is taken after it. The inventory opens on Tab without checking for text boxes, so while one of the panel's boxes has the keyboard Scry releases that key press first (`ZInput.ResetButtonStatus`), as the game does with a key it has handled.

## Preview copies

Every preview is a copy of the prefab made under an inactive holder, so none of its scripts wake. While it sleeps, everything is removed except what draws, animates, lights or sounds, plus a few of the game's effect scripts that need neither a network view nor a character (light flicker, random sound clips, timed destruction, fades). Scripts go first, then joints, then colliders and bodies, respecting what each component requires. Scripts added by mods are always removed, since what they need cannot be known. Only then is the copy placed and woken. It has no network view, so nothing of it is sent or saved. A location or room, which can hold thousands of parts, is made over several frames instead, a few milliseconds each (`Ghost.Building`): made asleep by Unity on a thread of its own and taken into the game a slice each frame (`Object.InstantiateAsync`, at once where that fails), then prepared, what is to go noted part by part and stripped a little each frame, then placed and woken a few parts at a time, no part woken with more than 64 under it, one holding more woken itself while its own parts wait (`WakeChunks`); the stage says its model is loading until all of it is awake. Waking any one part cannot be split. A bundle is let go of only once Unity makes no copy any more, and a copy dropped while it is being made is taken down once made, so switching away never waits on it. Stripping goes once through what is to go each pass, keeping in place what must wait for another component to go first.

Star levels, wear and the other looks the game switches by script are read from the untouched prefab and applied to the matching parts of the copy, found by their place in the hierarchy. A prefab of a hundred and fifty parts or more, such as the person, is stripped once and kept asleep, four at most, and later copies are made from that.

## Looks and gear

Where the game switches a prefab's look by script, one kind of look is offered: a plant's growth, a fire's state, a portal open or shut, a door, a chest, a windmill turning, a smelter or fermenter at work, a crafting station in use, a saddle, a pickable picked, a humanoid's gear, or an item's style. Each is set as the game's own method sets it (`Fireplace.UpdateState`, `Door.SetState`, `Smelter.UpdateState`, `ItemStyle.Setup` and so on), and those methods are among the ones the startup check fingerprints.

Gear goes on as `VisEquipment.AttachItem` puts it on: an `attach` part hangs on its bone, and an `attach_skin` part is bound to the body's bones. Armour made for a skeleton with a different number of bones is left off rather than drawn twisted. A creature that rolls its gear (`Humanoid.GiveDefaultItems`) gets a row for each list it rolls from, and one weapon in hand at a time, as its AI holds one in a fight; the items in hand set its stance as `Humanoid.SetupAnimationState` does.

An item shown worn goes on a copy of the player the same way, over whatever is kept on, and chest and leg armour paint the body with their own textures, as the game swaps them.

## Animations

The animator's switches only move it between states under conditions the game sets together, and those cannot be read at run time, so a switch pulled on its own often does nothing. Scry instead plays each clip of the controller directly on the copy through a playable graph, and destroys the graph when the clip ends.

A clip's events are answered by Scry when every event the creature's clips send is one the game's `CharacterAnimEvent` or `AnimationEffect` knows: effects play at the bone they name, props hang on their bone, parts show and hide, and a strike plays its attack. When a clip sends anything else, as some mods' clips do, its events stay off, since an event nobody hears makes Unity log an error each time.

Footsteps are not events in the game: its walk animations set a value that changes sign as a foot comes down, which a clip played on its own does not set. So while a moving clip plays, the feet named by the prefab's `FootStep` are watched, and a step sounds where one comes down, chosen from the creature's step table for the ground the stage shows (`StageGround.Footsteps`): the plain floor is the game's default ground, the sea's floor water (the feet stand in the water over it, and the game steps on water first), any other biome's ground the game's own for flat terrain there (snow in the mountains and the deep north, mud in the swamp, grass in the meadows and the black forest, ash in the Ashlands, ground in general elsewhere). The step played is the one the game would play (`StageGround.GameStep`): of those made for the way of moving, the last made for that ground, else the first made for the default one; where the game would fall silent the stage goes on to ground in general, then to steps made for another way of moving, then to the first it has (`StageGround.StageStep`), so no creature is mute on the stage. A swimming creature steps on water as in the game, and only with a step made for swimming. `StepGround` holds the game's grounds by value, as a test holds.

### What the animator plays

Which clip a trigger or switch leads to cannot be read either. So once per creature (and for the person, once per weapon stance) each is pulled on a hidden copy and watched beside a run left alone, both seeded alike since the game picks idle clips at random (`RandomIdle`). The watch takes about four milliseconds a frame, stops when another entry is chosen, and waits while the panel is closed. A watch that fails is tried once more, then given up and told in the log.

An attack is watched as the game watches one (`Humanoid.InAttack`): every clip played while in a state tagged "attack" is the attack's, in order. The same watch finds where the game's own actions lead: jumping, eating, sleeping and waking, being alerted, dying, staggering, spawning, swimming and flying. Where the watch could not see a swim or a jump at all, clips named for them are paired by their names and listed apart under *Found by name*.

### Attacks and what clips play

The game gives creatures their attacks as items and starts each by an animator trigger, so an attack plays through its clips. As its first clip starts, its start and trail effects play where the attack comes from (`Attack.GetAttackOrigin`); when a clip says it strikes, its trigger plays, and its hit plays where it lands: a swing's where a target within its attack range would stand, an area attack's in its middle, a throw's where the thrown thing lands. An attack none of whose clips says when it strikes strikes halfway through its first.

A clip one of the game's actions leads to plays the effects the game plays with that action. Some clips the game plays nothing with, yet something is heard around them, and those are listed under *Heard around it*: an alert call after waking, the idle sound with idle clips (`BaseAI.DoIdleSound`), and a hit with a stagger.

## Effects

What an effect list's chip does is one rule (`ChipPlan`): a creature's death with a ragdoll falls as the ragdoll; a list the game plays when destroying the prefab destroys the copy; a tree's hit shakes its trunk; a jump, death, alert, waking, eating or block sets the animator as the game does; an item's attack plays in the clip the person swings it in; a list the game plays with a clip plays that clip; anything else just plays.

A destroyed copy is hidden while what it leaves falls, then stands again. What falls is what the game leaves: debris thrown as the game's `Gibber` throws it, the piece's own parts when it breaks apart (`Destructible.CreateFragments`), a tree's log tipped away from you off its stump, which stands solid as the game's does, so the log's far end striking the ground is a contact of its own and plays the log's impact (`TreeBase.SpawnLog`, `ImpactEffect.OnCollisionEnter`), a log's halves (`TreeLog.Destroy`), what a rock leaves in its place (`Destructible.Destroy`), and what a drop table rolls.

Falling copies keep their bodies and colliders on Scry's own layer, which meets only the ground and itself, so in the world they land on the real ground while players, creatures, arrows and the game's checks pass through them. A body is pushed out of what it overlaps no faster than the game allows (1 m/s), so a log's halves part gently. On the stage they land on an invisible ground under the model.

What a model plays is shown at the size the model is shown, so at twice the size its hits, steps and effects are twice as big. A sound or effect lists under *Plays in* the effect lists it is part of, lists alike merged into one row. A play button stays lit until everything it started has finished, and a second click stops it.

A status effect with something to see shows on a person on the stage, its start effects placed where the game places them on a character. The status effect itself is never applied.

Volume, size and animation speed sit in the header as small icons beside the name, a speaker, a double arrow and two arrowheads, each opening a short slider in a box under it, lit while its value is not the selection's own (`ScryPanel.Slide`, `HeaderSliders`): size on a curve from a tenth to ten times, caught at the selection's own size near the middle, and only while the stage shows a model; animation speed from still to three times, caught at its own a third of the way along, where the selection has animations. Beside them a ring is the one Repeat for whatever plays, clips, effects and sounds alike, lit while on and remembered with the panel's place (`Previews.Repeat`); a click on the value puts it back, the wheel over the box nudges it, and Escape, a click elsewhere or another selection closes it. The box takes the mouse before anything under it and is drawn over everything. *Adjust* keeps stars, wear, look and a projectile's speed, and shows only when one of them is there. The volume slider plays the selection from silent to twice the game's loudness, in steps of 5%, and goes back to the game's loudness with every new selection, so a sound turned up never carries over to one that plays as soon as it is selected. An audio source cannot go above full and the game's sound script sets its volume on every play, so Scry's copies carry a small audio filter (`OnAudioFilterRead`) that scales the samples and clips them at full scale. The game's own sounds are left alone.

## What the details tell

### Where things come from

With the catalog, Scry reads where things live and where they come from: the running spawn systems' lists, spawn points, raids, nests, the world's vegetation, every drop table on any prefab (an item tells its share of a roll in each, how many rolls and how often, as `DropTable.GetDropList` rolls it), every station that turns one item into another, what producers make, what traders sell, and which boss each altar summons with what; an altar of item stands, such as Moder's, takes no offering but needs every stand of its prefix within its range filled (`OfferingBowl.Interact`, `FindItemStands`), so it tells the stands' item and how many stands. Items learn what they are used for: recipes, pieces, stations, fuel and what eats them. Status effects learn what gives them. Rows longer than twenty show eighteen until asked for the rest. Each way something gives a thing is read as figures, not words (`SourceFacts`: a creature's drop, a drop table's entry with what the table belongs to, a picked or grown thing, a producer's pace, a trader's ware, young born, grown up or hatched), and the model tells it (`SourceWords`), the same words on every page, with how sure it is to give the thing.

### The game's rules

Where a detail follows one of the game's rules, it is worked out as the game's code does, and that code is among what the startup check fingerprints. An item's facts follow its tooltip (`ItemDrop.ItemData.GetTooltip`), gear's changes while worn in the tooltip's order (eitr regeneration, then `Player.AppendEquipmentModifierTooltips`: building tools', jump, attack, block, dodge, swim, sneak and run stamina and heat resistance as a percent, the most adrenaline as a number, `GearWords`), and what full adrenaline gives; armour's own resistances count while worn on the chest, legs, head or shoulders (`Player.ApplyArmorDamageMods`) and a shield's or weapon's while blocking with it (`Humanoid.BlockAttack`), so they are told as such and anything else's not at all; a weapon's second attack, which the game offers only with an animation of its own (`ItemData.HaveSecondaryAttack`), is told against the first (its damage, knockback and stagger multipliers) with what it costs (`CombatWords.SecondaryAttack`); creature drops follow `CharacterDrop.GenerateDropList`, which leaves the top of each range out and doubles marked drops per star; sight follows `BaseAI.CanSeeTarget`, which measures the view angle to either side of forward, so the field is twice that angle; a creature turns on what it sees nearer than its alert range, less while the target sneaks, and gives up a chase beyond its chase distance from where it spawned (`MonsterAI.UpdateAI`, `MonsterAI.UpdateTarget`); a weak spot's resistances take the place of the body's for a hit that lands there (`Character.GetDamageModifiers`); a piece's support comes from calling the game's own `WearNTear.GetMaterialProperties`, is lost per metre between pieces as `WearNTear.UpdateSupport` loses it, and rain, ash and snow wear it as `WearNTear.UpdateWear` does; a spawner checks every two seconds and spawns once its timer is past its interval, so a 10 s interval spawns every 12 s (`SpawnArea.UpdateSpawn`), picks by weight (`SpawnArea.SelectWeightedPrefab`) and rolls each further star on its own (`SpawnArea.SpawnOne`); raids are rolled every so many minutes at a chance and one is picked among those that can start (`RandEventSystem.UpdateRandomEvent`, `StartRandomEvent`), come for a player in their biomes with a base value of three within 20 m where they need a base (`GetValidEventPoints`, `CheckBase`, `EffectArea.GetBaseValue`), and bring each creature every so often at a chance while fewer than its cap are near (`SpawnSystem.UpdateSpawnList`); stars add health as `Character.SetupMaxHealth` and damage as `Attack.GetLevelDamageFactor`; upgrade kits are asked for only at the upgrade station (`CraftingStation.m_upgrader`), and comfort counts only the best piece of each group (`SE_Rested.CalculateComfortLevel`); a tame creature breeds as `Procreation.Procreate` has it, when fed and not alerted, with a partner of its kind (or the one it names) near unless it has young alone too, gaining a love point each check the game does not skip (it skips at the chance it calls the pregnancy chance, so a point comes at the rest), pregnant once it has enough, and stopping once too many of its kind and its young are near (`BreedWords`); its young has its stars and grows up after a time into what it names, by weight among several (`Growup`), and an egg hatches lying on its own, by a fire and under a roof with enough cover as it asks (`EggGrow.CanGrow`); a creature's saddle tells what it is ridden with and its stamina then, regained slower when hungry and drained by running and swimming (`Sadle`, `RideWords`).

The game's plain damage, which no resistance lessens (`HitData.ApplyResistance`), is called "true". Numbers are the prefab's own. A world whose settings change them says so and by how much, without changing the figures.

A status effect lists what differs from a fresh one of its type, and a stats effect tells its stats as the game's tooltip does (`SE_Stats.GetTooltipString`). Which mod added a prefab, a status effect or a location comes from four clues in turn. First Jotunn's registry, read by reflection so Scry does not depend on Jotunn: its prefabs, items, pieces, status effects, creatures, vegetation, clutter and locations, and its recipes and station conversions, so an item made by a recipe or conversion another mod added says *added by* that mod on its row (`ModWords.AddedBy`). Then the scripts on it: a mod's prefab carrying scripts from one mod's assembly, none of which is on any of the game's own prefabs (as a mod putting its script on every piece would make it), is that mod's, and a status effect of a class from a mod's assembly is that mod's. Then the asset bundles: the mod shipping a bundle that holds the prefab by its name, and failing that the mod shipping the bundles that hold what it uses, its sounds' clips and its icons, or for an effect with neither its materials' pictures (`AssetsOf`). Clues naming several mods leave it unnamed rather than guess (`ModAttribution`). Jotunn's assembly and Scry's are no clue, and the self-test counts what each clue named and checks that nothing of the game's own is put down to a mod.

### Mods hooking into the game

A mod can also change what the prefabs say without touching them, by hooking into the game's own code: Jewelcrafting adds gems to a creature's drops as it dies, Epic Loot rolls tables of its own and spawns what they give. Scry reads which mods do so from Harmony's record of every patch (`Harmony.GetPatchInfo`), each patch's mod being the plugin whose assembly holds it (`ModHooks`): hooks into what a creature drops (`CharacterDrop.OnDeath`, `GenerateDropList`, `DropItems`, `Ragdoll.SpawnLoot`), into what a drop table, chest filling or pickable gives (`DropTable.GetDropList`, `GetDropListItems`, `Container.AddDefaultItems`, `DropOnDestroyed.OnDestroyed`, `Pickable.RPC_Pick`, `Pickable.Drop`), and into spawning (`SpawnSystem.IsSpawnPointGood`, `UpdateSpawnList`, `Spawn`, `SpawnArea.SpawnOne`, `CreatureSpawner.Spawn`). A creature's death (`Character.OnDeath`) is hooked for many reasons, so a hook there counts only when its own code names a drop list's type or a member of it (`IlShape.Names`, each token resolved by the hook's module). A creature then names the mods hooking into its drops and, where it spawns by itself, into its spawning, and anything whose drop table holds something names those hooking into what it gives (`ModHookWords`); the details stop short of saying what they change, which only the mods know. A method a game update renamed is told as a fault rather than leaving its mods unnamed.

### More of the game's rules

The same goes for the rest of what Scry tells, each rule by the methods deciding it: comfort (`SE_Rested.CalculateComfortLevel`, `GetNearbyComfortPieces`), a smelter's, cooking station's and fermenter's working (their `Update`, conversion and item checks, `GetFermentationTime`), a beehive's and sap extractor's making (`Beehive.UpdateBees`, `SapCollector.UpdateTick`), a fire's fuel (`Fireplace.UpdateFireplace`), wear and support (`WearNTear.UpdateWear`, `UpdateSupport`, `HaveRoof`, `GetMaterialProperties`), costs (`Recipe.GetAmount`, `GetRequiredStation`, `GetRequiredStationLevel`, and `Player.HaveRequirements` and `ConsumeResources` when the hook names a requirement's amount), item stats (`ItemDrop.ItemData.GetDamage`, `GetArmor`, `GetWeight`, `GetMaxDurability`, the blocking ones), eating (`Player.EatFood`, `CanEat`, `UpdateFood`), growing and growing back (`Plant`, `Pickable.UpdateRespawn`), the weather (`EnvMan.UpdateEnvironment`, `GetAvailableEnvironments` and how wet, cold and freezing are found), raids (`RandEventSystem`'s rolls and checks), taming and breeding (`Tameable`, `Procreation`), trading (`Trader.GetAvailableItems`) and container sizes. A station's, piece's or container's `Awake` is hooked for many reasons, so a hook there counts only when its code names the settings the rule is read from (a smelter's `m_secPerProduct`, a container's `m_width`), or when it is a transpiler, which rewrites `Awake` itself (AzuContainerSizes does so). Each note stands beside what it concerns: a piece's comfort, wear and cost, an item's stats, food and recipe, a station's working, a plant's growing, a creature's taming, a raid and its weather, a trader's wares, a container's slots. An entry's page tells every rule mods hook into there in one soft line after everything else, what they hook into and how many mods, marked as unsure; hovering it names each mod and what it may change (`ModHookWords.Line`, `Tip`). A mod's page and the report name every rule it hooks into, and the *Mods* tab lists those that only hook in under *Hooking into what Scry tells*.

A chest, cart or ship tells how many slots it holds, in rows as its inventory shows them (`Container.m_width` a row, `m_height` rows, `ContainerWords`), from its own container or, for a cart or ship, the one on a part of it.

A piece says where it may be placed, as `Player.UpdatePlacementGhost` refuses it: kept a distance from pieces it names, near or on top of the one it must connect to, on the ground, cultivated ground or dirt only, on water or not in it, not on wood, not on a slope, under a ceiling only, not on a floor, in a teleport area, in the Deep North's deep snow or one biome only, and in dungeons when it allows it (`BuildWords.Placement`). A station's upgrade names its station, how near it must stand and how far from its other upgrades; a station says how far from it its pieces may be built, more with each upgrade (`CraftingStation.m_rangeBuild`, `m_extraRangePerLevel`), and whether crafting needs a roof or a fire. Each area a prefab holds says what it does, by where the game reads its kind (`AreaWords`): warmth for resting and beds, fire that fire-shy creatures avoid, a base that keeps the world's spawning and spawners out and counts toward raids, flames a cooking station needs, a teleport area, ground untamed creatures keep out of, warm and cozy ground the cold does not reach, with its reach from its sphere and any effect it gives; a private area the game reads nowhere is not told. A bed says that claiming it makes it where you come back to and needs a roof and 80% cover, and that sleeping needs night, no enemy sensing you, the same cover, a fire and being dry (`Bed.Interact`).

### Raids and biomes

A raid's biomes, which its biome chips and the biome pages follow, are where the game rolls it (`RandEventSystem.InValidBiome`): those set, or every biome where none is set; a boss's fight and what something else starts are never rolled by biome, so they have none (`RaidGrouping.Biomes`).

Each biome the world's weather is set up for (`EnvMan.m_biomes`) is an entry of its own in a *Biomes* tab, listed in the order players meet them, several setups of one biome taken together (`BiomeSource`). A creature's biomes are its home: those its world spawns name, but where a spawn asks for a weather, only the biomes with that weather of their own (`SpawnBiomes`); one only a world event brings (Fimbulvinter's, an invasion's) makes no home, so a Jotun or a charred warrior is no longer told living in every biome. Its page tells each weather with how likely it is, as the game picks one by weight (`EnvMan.SelectWeightedEnvironment`), the most likely first, and what it does (`WeatherWords`); its music by the time of day, each playing when clicked and Enter playing its day's; and what lives, grows, stands and comes there, from the other entries' biomes, each a chip going to it (`BiomeWords`): its creatures, its fish, what grows wild (a plant a mod made buildable too), its places and raids, what else the world places there, and what comes there only in weather a world event brings. *Everything here* searches for all of it. An entry's biome chips go to the biome's page, or search where a biome has none.

### How pages read

Resistances show as a grid of the ten damage types in the game's order, the same on every creature, damageable piece, rock and tree, each cell the share of that damage taken as `HitData.ApplyModifier` scales it (75, 50 or 25% resisted, 125, 150 or 200% for weakness, 0% for immune or unaffected), coloured by how it lands, the game's word on hover (`ResistWords`). Up to five cells stand in a row, fewer where the side is narrow. Armour's and a shield's own show as a grid when they resist anything, else as a line saying they resist nothing; a weak spot stays one line, telling how it differs from the body.

Pages of one type show the same rows a player looks for, saying "none" or "no" where that is the answer rather than leaving the line out; a "none" nobody asks about is left out, so pages stay short. A creature always tells its attacks (a hunting one with no attack Scry can read says so as unsure), weak spots, whether it can be tamed and its drops, and an animal that it only flees (`AnimalAI.UpdateAI`). Every item tells whether it goes through portals; gear how far it upgrades, its wear (or that it never wears out) and where it is repaired or that it cannot be (`InventoryGui.CanRepair`, `ItemWords`); armour its armour, movement, set bonus and what it resists or changes while worn; a weapon or shield its block and a weapon its second attack. Furniture tells its comfort, a piece some tool builds its cost (free where it is), and what breaks its tool tier ("any") and that it gives nothing where it does.

Lists of content come in one order on every page (`ContentOrder`). Loot comes rarest first: a creature's drops by their chance, a drop table's items (a chest's filling, what a rock or a tree gives) by their weight, which within one table orders them as their chance does, a place's chests and pickups by how likely each is there, and the loot of a dungeon's rooms in the fewest kinds of room first. Creatures come toughest first, bosses and then the most health: on a biome's page, at a place's or its rooms' spawn points, in a raid and in a nest. Where a thing comes from comes surest first, each line knowing how often it gives the thing (`SourceWords.Sureness`: a drop's chance, about how often one opening of a drop table gives it as `DropTable.GetDropList` rolls, a nest's share, everything else always), equally sure ones by the biome players reach first, and the places it is found in go by the biome of the location going by each, then by name. On a biome's page what grows comes hardest to gather first (the tool tier it needs, then its health), places the fewest the world places first (`ZoneLocation.m_quantity` over every set of rules it is placed by), raids in the order the Raids tab lists them, fish and the rest by name. Each order keeps names in order among equals, and what the game itself lists in an order players see in play (a trader's wares, a station's recipes, a recipe's ingredients) keeps it.

Scry is sure of what it reads from the game's data and of what it works out by the game's own rules, whose code the startup check watches. The rest it tells as its best knowledge, marked with a `~` before the label, in a softer colour, saying why on hover (`UnsureWords`): a mod named by clues rather than by Jotunn's registry, where the mod registers what it adds (the clue each thing was named by is kept, `Entry.ModClue`, and a mod's page lists clue-matched things in rows of their own); every note on mods hooking into a rule, as only the mod knows what its code does; what was seen dropping in play, which is not the odds; an item or creature Scry found nothing giving or placing, which something it cannot read still may; a skill a mod adds that it names nowhere Scry reads; and the report's things not placed.

*In the game* is laid out by topic for the kinds laid out so far, creatures, items, pieces, resources, projectiles and places (`FactLayout`): topics in an order fixed for the kind, each under a small heading; a few headline numbers as tiles, a set of them chosen by what the thing is (a creature's health, faction, how it moves, whether it can be tamed, and what it sees and hears; a weapon's damage, weight, quality and wear, armour's armour and movement, food's food); the list of where it comes from and what it is used for under their topic's heading without a title of their own; what qualifies a row told under it as a note (a creature's drops with stars and the world's rate under its drops); every fact read shown once, going to a topic by its label, else by the part of the reader that told it (`Facts.PairParts`, `Row.Part`, noted as each part reads), else to *More* at the end. The other kinds keep their facts, rows and blocks in the order they always had, until they are laid out.

A page's name stays in sight while its sections scroll under it, and a line under the name names each section, with how many it holds where its heading tells it (`SectionLine`, `ScryPanel.SectionLine.cs`): a click brings that section's heading to the top, as far as the page scrolls, opening it where it is folded, and the section being read is lit, the one a click went to while the page stays there, else the last whose heading has come within the top third, or the last of all at the page's end. Each heading notes where it stands as the sections are drawn, and the line, drawn before them, is laid out from where the last draw found them; a page of one section has no line.

### What follows from what

A creature whose defeat sets a world key (`Character.m_defeatSetGlobalKey`) tells what follows: the raids that may then come and those that stop (`RandomEvent.m_requiredGlobalKeys`, `m_notRequiredGlobalKeys`), what the world's spawning and spawners then place and what spawners stop placing (`SpawnData.m_requiredGlobalKey`, `CreatureSpawner.m_requiredGlobalKey`, `m_blockingGlobalKey`), and what traders then sell (`Trader.TradeItem.m_requiredGlobalKey`), each kept as the catalog reads them (`UnlockBook`). A world set to pick raids by each player's own progress checks other keys, so its raids are not told under a key.

A copy let fall strikes the ground as its prefab does: the copies keep none of the game's scripts, so where the prefab has an `ImpactEffect` (a felled log has one) Scry plays its hit effect where the copy strikes, faster than its least speed and no sooner than its interval, on the stage as the stage's and in the world where it strikes (`Thud`); it deals no damage. Everything a felling or breaking leaves on the stage is heard as if beside you, the log's own sounds too.

A ballista names the ammunition it fires, how many shots it holds, whom it shoots within its sight and how often, and the trophies that, given to it, make it shoot only their creatures (`Turret`, through `BaseAI.FindClosestCreature`); a trap on whom it springs, when it rearms, the damage of what it sets off and whether it staggers (`Trap`, its `Aoe`); a ship whether the Ashlands' boiling seas burn it and what it takes capsized (`Ship.TakeAshlandsDamage`, `m_upsideDownDmg`); a cart its own weight and how much of its load counts (`Vagon.UpdateMass`); a catapult what it loads by item type, with the items it always or never loads, and that it throws whoever stands where it is loaded (`Catapult.CanItemBeLoaded`, `CollectLaunchCharacters`). The words are `MachineWords`.

A fish names the baits it bites on, each with the chance it bites once it reaches the hook (`Fish.TestBate`), and a bait the fish it catches; a locked door names its key and whether it is used up (`Door.m_keyItem`, `m_consumeKey`) and a key the doors it opens; a boss stone's stand gives a Forsaken power for the trophies it takes (`ItemStand.m_guardianPower`, `m_supportedItems`), so a trophy names the power it gives there and a boss dropping it names its power. Each is read from the catalog's own prefabs, boss stones and dungeon doors among them as the networked prefabs they are.

Young come from somewhere too: a breeding creature's young is born to it, a young one grows up into what it names and an egg hatches into what it names, and each is told on the other's side as where it comes from (`Knowledge.Breeding`), so a mod's foal or a hen's chick has a source like any spawn.

### Mods

What a mod adds as a creature dies shows once it is seen: Scry watches the loot of every death whose loot comes out on this machine (`DropWatch`), whichever mod put it there, and keeps it in `BepInEx/config/isimp.Scry/seen-drops.txt`, written at most every half minute and on quitting, so it grows from session to session. A death drops its loot at once (`CharacterDrop.OnDeath`, while its drops are on) or through its ragdoll as that goes (`Ragdoll.SpawnLoot`, the creature noted when `Ragdoll.Setup` is given its loot); every item that comes to be (`ItemDrop.Awake`) while either runs, the game's and any a mod spawns in its own hook there, is counted as that creature's, first and last among the hooks so a mod's are inside. Each death is a kill of its creature, and each item is counted with the kills it came in and the fewest and most at a time (`SeenDrops`). A creature shows *Seen dropping in your play* with how many kills that is from, an item names each creature seen dropping it among where it comes from, and an item seen dropping has a source in the mod report. The hooks only watch and change nothing. Loot another player's machine makes is not seen, nor loot of a ragdoll set up before the game was started; what is seen is what happened, not the odds, and a rare drop may not have come yet.

Every mod loaded (`Chainloader.PluginInfos`) is an entry of its own in a *Mods* tab, made last, once every entry knows the mod that added it. Its card tells its version and id, and its page what it adds, a row for each kind, its stations and tools with what Scry links for each, which of the rules above it hooks into, and what Scry could not place (`Facts.Mods`). An entry a mod added goes to that mod's page from the line naming it.

A mod manager installs each mod in a folder named for its package ("Author-Name") with the package's `manifest.json`, `icon.png` and `README.md` beside it (`ModFolders`): the nearest folder above the mod's assembly holding a manifest, short of the plugins folder itself, is its package. Its page then starts with the manifest's description, says who made it (the folder's name before the package's) and gives its website, opened in the browser on a click and only when it is an http or https address; the manifest is read by a small reader of Scry's own (`ModManifest`). Its icon, made 96 pixels a side at most, stands for it in the list, on its card and on chips, read a few at a time as the catalog is made and kept from world to world. Its readme shows under *README* as plain text (`ReadmeText`): headings and paragraphs, list items as bullets, table rows as their cells and code as it is, with pictures, badges, markup, link targets and comments left out and the web's escapes (`&lt;`) read; it stops at a paragraph after 6,000 characters, the rest staying in its file. A mod dropped into the plugins folder by hand has none of these.

The mods tie together as they declare it (`ModLinks`): BepInEx's dependencies, hard (the mod does not load without the other) or soft (it works with the other when it is there), and incompatibilities, each by the other's id, and the package's dependencies, each by package, which brings every mod that package holds. A page lists the mods it *Needs* and those that need it, those it *Works with, when there* and those that work with it, each a chip going to that page, and names the mods it *Will not run with*, by name when loaded and by id otherwise. A mod needed is not also listed as worked with, no mod needs itself or a mod of its own package, and what is no mod loaded (BepInEx itself, a library without a plugin) is left out.

The mod report sums up each mod (`ModReport`, read from the catalog by `ModReportReader` when it is opened): how many of each kind it adds, its crafting stations with what is made at each, built near it and upgrades it, its build tools with how many pieces each builds, which of the rules above it hooks into, and what Scry could not place: a station nothing is made or built at, an item with no recipe, drop, maker, trader or location Scry sees and that no creature carries (a creature's own attack is an item it carries), a creature no spawn list, spawn point, altar or location places, a piece in no build menu. A mod's own page is Scry's, so a mod that adds nothing and hooks into none of these is not in the report, and its page says so. What could not be placed may come from the mod's own code; until every location is read, what is found only in locations counts as having no source. It takes the list's place, as the search's help does, from the bar above a list showing only what mods added, or with `/scry mods`; a mod's name goes to its page, and every station, tool and thing not placed is a chip going to it. Changing the list (the search, a tab, favourites, recent or where things are from) puts the list back; going to an entry from the report leaves it open.

## Locations

### Reading them

Where things are found in the world's locations and dungeon rooms is read only on request: with *Read all locations*, with `/scry locations`, or by itself when `ReadLocationsAutomatically` is on. The game keeps locations and rooms as soft references to asset bundles it loads while building a zone, and loading its 550 or so at once stalls the game for seconds. So one at a time is loaded in the background, read three milliseconds a frame, and released: two to three minutes in all, about two seconds of it Scry's own work. Only names are kept. Nothing shows until all is read, so a reading can be stopped at any point and leaves the world as it was. A place in an entry's *Found in* goes to the location of that name, the first one where several share it, as the variants of a dungeon do; a dungeon room's place is its dungeon's (`Places.LocationNamed`). A place no location goes by, a mod's room no dungeon here is built with, searches for what is found there instead.

Every location and room has an entry from the start, made from what the game keeps of it in memory without loading its bundle: a location from the world's location list (`ZoneSystem.m_locations`, one entry for all the rule sets of one prefab), a room from the dungeon database. A location's details tell the rules each rule set places it by, as `ZoneSystem.GenerateLocationsTimeSliced` applies them to every point it tries, each rule left out while it is at its default. Woods are told by the forest factor (`WorldGenerator.GetForestFactor`), noise from 0 for the thickest woods to about 2.2, with the Meadows wooded below 1.15. The ground value a location asks for is the lava in the Ashlands (from 0.6 the game counts it as lava), the Mistlands' growth, and 0 in every other biome (`WorldGenerator.GetBiomeHeight`), so there a minimum is never met and a maximum always is; a check of the surroundings, which keeps spots with more of that value around them than the average spot meeting the other rules, is left out where the biome has none, as there it measures nothing.

### On the stage

Selecting one loads its bundle in the background and holds it while it is shown, one at a time; the stage says so while it loads, and a bundle that cannot be loaded says so there and in the details (`PlaceAssets`). Once loaded it is read (`PlaceReader`): its game name, the networked parts it places with how many and how likely, the creatures its spawn points place, where its vegvisirs point, the levels it sets for its spawn points, how far around it nothing can be built, how a dungeon or camp in it is built, and a room's box, kind and doorways. A part's chance multiplies every roll above it, as `ZoneSystem.SpawnLocation` and `DungeonGenerator.PlaceRoom` roll them: each `RandomSpawn` at its chance, each `RandomObject` picking one entry by weight (an entry without an object leaves the whole pick out), and a `RandomSpawn`'s object for when it is off the rest of the time. Its entry then takes the game's name, and *Read all locations* fills every entry the same way. Its page tells its parts in a row by what each is (`PlaceParts.RoleOf`): chests and pickups, what is gathered (rocks, trees and ore, and what only breaks), the rest (spawners, creatures, stations, beds, fires, altars, item stands, vegvisirs, runestones, portals, traders), then the creatures its spawn points place, and its building pieces last under *Built of*. A chest or a pickup counts as one whatever else it is, a spawner or something used for what it does goes with the rest even when it is built, and something mined or felled is gathered even when it is a piece.

The stage copy is rolled the same way while it still sleeps, so the prefab itself is never touched (`PlaceCopy`), and *Roll again* makes a new copy with new rolls; it shows only for a place where something is left to chance, its creatures included. The wheel zooms toward what is under the pointer, which stays under it, as near as two metres however big what is framed (`StageCamera`), and a drag with the right button keeps what was grabbed under the pointer. With a floor opened the camera looks at that floor: at its height, over the middle of the rooms of the example standing on it (or of the whole place), framed on how far they reach, gliding to the next as floors are stepped; what is under the pointer is then found on that floor, and a drag moves the view along it. The camera stays over a floor's cut, as a cut only opens what is seen from above it: raised by Shift and the wheel or by the ruler, the cut takes the camera up with it, and the wheel comes no nearer than keeps it there (`StageCamera.OverCut`). A location's *Biome* line goes to the biome's page, or names its biomes as chips where it has several.

### Their creatures

Its creature spawn points (`CreatureSpawner`) put their creatures on the stage with it, a dungeon's or camp's rooms each with their own, rolled as the game spawns them once you come near (`SpawnPoints`): a point on its own always spawns; points of one group within their two radii of each other, step by step, keep up to their most alive, each picked by weight among those not yet spawned (`CheckGroupSpawnBlocked`, `Group.SpawnWeighted`); a group the location blocks spawns nothing (`Location.m_blockSpawnGroups`). Each creature's level goes up from the point's least while a roll under its chance holds, to its most, the location's overrides applying to every group it does not leave out (`CreatureSpawner.Spawn`), the chance as the world has it (`SpawnSystem.GetLevelUpChance`, its world level or enemy level-up rate; the share a world sector adds is left out, as the stage stands in none). Every point is rolled whatever the world's progress or the time of day.

The points are read off the copy while it sleeps, before stripping takes them off; each creature stands on the first solid thing straight down from a metre above its point, as the game drops what it spawns (`ZoneSystem.FindFloor`, on the layers it counts solid, noted off the copy while it sleeps, as awake it is all on the stage's layer), or at its point where nothing is under it; one that flies (`Character.m_flying`) is as high over that ground as its AI keeps it at the least once it takes off (`BaseAI.m_flyAltitudeMin`) (`SpawnPoints.Rise`). Each faces a way of its own as the game turns one it spawns, dressed and starred as a creature selected is, held in its first pose (its animator evaluated once and switched off, to spare the frame) and muted, hung on the point so it goes with what holds it, dimmed with its room. A few are made each frame. They stand on a second free layer, the next unnamed one below the stage's or else one of those Unity keeps spare under 8 (7, 6, 3), as a game with mods can have every layer from 8 up named but one.

A floor's cut, the near plane laid along it, cuts them with all else; one whose ground is above the cut stands on a floor above and stays cut away with it, on the stage's own layer while the cut is there (`SpawnPoints.AboveCut`); what of them is above it is then drawn again over the picture, by a projection whose far end lies along the cut and whose depth is cleared first (`StageCamera.AboveCutRow`). Nothing below the cut can stand before what is above it, as the camera looks from above, so a tall creature stands whole and what stands before its lower part still hides it; with no second free layer they are cut as everything is. The stage's *Creatures* chip puts them away and back, and is remembered.

### What the copy leaves out

A part's own conditions (a biome, a height, lava, a dungeon's kind) are not applied, since the copy stands in no world. A dungeon's interior is left out of the copy: the game builds it some 5,000 m above its entrance, and a camera framing both would frame neither. So is an `EnvZone`'s view of the outside, which the game draws only for someone inside. A location stands on its root, where the game stands it on the terrain, so what reaches below it is under the floor as it is under the ground; a room stands on its lowest doorway, the floor it is walked into on (`PlaceView.Ground`).

### Floors and the cut

A room opens on the stage cut above head height (2.5 m) over its top floor, looked down into; a location keeps its roof, and a new copy of the same (rolled again) keeps the cut it had, its roof on or the floor opened where it still has it (`FloorCut`, which keeps the floors, the floor opened and the cut's height).

Its floors are found in the place itself (`FloorProbe`, `FloorFinder`): its copy is made with its colliders kept, rays are cast straight down over it on a grid every half metre (at most forty along its longer side), each going down through every surface it meets rather than only the first of each collider (a cave room's rock is one collider, the top of its rock and its floor both), and where they land on what is flat (about 18 degrees at the steepest, so a roof, whose pieces lean 26 or 45 degrees, or a ramp is none) is counted in bands of a quarter metre, each with the bands either side. What has nothing of the place above it, half a metre or more, is open: a flat roof's top, a cave's rock over its hollow, a tower's open deck, seen with the roof on and no floor to cut to. Only ground one can stand on counts: a spot whose neighbours all four ways landed in the same bands, so a beam, a table, a bed or a single stair step adds nothing.

A band whose such spots hold 2 m² and 1.5% of the place's ground is a floor, those with the most room first; in a dungeon's example each room's own floors are floors however little of all the example's ground they are, as they are when that room is shown alone: its main ground, where it has the most room (2 m² at the least, `FloorFinder.MainFloor`), and each level holding its share of the room's own ground, as a deep chamber's floor or a hall's gallery is in a big example; a room standing whole on none of them, a sloping corridor with no flat ground, gets a floor at its lowest doorway, where it is walked into (`PlaceView.ReachingEveryRoom`); and one within 2 m of a floor already taken is part of it (a step, a dais). Each room of an example is a patch of its own, its spots never neighbours of another's; each room's rays are summed up once, band by band, as it comes in (`FloorPatch`), and the example's floors come from those added up, so a dungeon of a hundred rooms finds its floors as quickly as one of ten. The colliders are taken away once read. A location's ground, its root, is a floor too where none was found near it, as bare earth is the world's own; a room with nothing found keeps its doorways' heights (`PlaceView.Floors`), and a dungeon's example is read room by room as it is built, its floors renewed as rooms come in; while its entrance is shown, each room is woken alone to be read, beside the sleeping example.

Each floor is cut at head height, or just under the floor above where that is lower (0.6 m under it, but never lower than 1.4 m over the floor), so a low storey's ceiling goes whole and what stands on the floor stays (`PlaceView.CutHeights`).

The roof button over the ruler takes the roof off, opening the floor last opened, and puts it back, lit while the roof is on; Page Up and Page Down with the mouse over the stage (over the list they page it) step a floor down, staying on the lowest, or up, and from the top floor put the roof back (`PlaceView.StepCut`). The ruler at the stage's right edge has a tick for each floor and a bar where the cut is: a click on a tick opens that floor, a click or drag elsewhere cuts there, over the floor below it (`PlaceView.LevelAt`), above the top floor puts the roof on, and the wheel over it steps floors. Shift with the wheel moves the cut too.

The cut is the camera's near plane laid along that height (`Camera.CalculateObliqueMatrix`), so it opens any model whatever its meshes; the far plane, which the oblique projection tilts, is pushed out to keep the backdrop, and from below the cut nothing is cut (`Stage.Cut.cs`).

### Runestones and music

A place's runestones are read with it (`RuneStone`): every text each can give, the one it has or every one of its random texts, with their titles, a stone told once however often the place holds one alike (`PlaceRunes`). A stone with several texts gives one picked with its place in the world as the seed (`RuneStone.GetRandomText`), so a stone always gives the same one, which its section says. They show under *Runestone texts*, which folds like the other sections.

A place's music is read with it: a source of its own that `MusicLocation` starts on coming near, a piece of the game's music list that `MusicVolume` starts on stepping inside (at its chance, unless it fades in by distance), and the music of the weather an `EnvZone` sets inside (the environment's day music, else its night, morning or evening music). Enter, or a click on the *Music* line, plays the first that can be found (`MusicPreview`): the place's own clip from its loaded model, or a named piece's clip from `MusicMan.m_music`, once through, at your ears in the game's music mix and at your music volume. The game's music is muted meanwhile rather than stopped, so it goes on underneath and is heard again when the piece ends, when Enter stops it, or when anything else is selected or played.

### Example layouts

A dungeon's rooms and a camp's tents are built when the game makes the zone, so under a dungeon's or camp's details an example layout stands in for them. The rooms of its kinds are loaded one at a time in the background and read, which fills their own entries too (`ExampleLayouts`), and then laid out by the rules `DungeonGenerator` follows for a new one, in Scry's own code and with dice of its own (`DungeonLayout`): a dungeon from a random entrance whose way in is at the generator, a room at a random open doorway for each try, stopping early once its required rooms are in, end caps and dividers on what is left open, and a door rolled for each doorway between rooms (a dungeon's details name the doors in a row for each type of doorway, how many of the doorways that allow one get one, each door listed alike likely at its own chance or the dungeon's, `DungeonWords.DoorRows`); a camp on a grid or scattered in a ring and walled.

A room may not overlap one placed before it, tested a tenth of a metre smaller (`Boxes.Overlap` stands in for `Physics.ComputePenetration`), nor leave its zone's box, which lies round the generator as a new zone puts it (`DungeonLayout.Site`). The ground's tilt and height, which keep camp rooms off steep or low ground, play no part.

Its plan is drawn in the stage's lower left corner, from above, turned with the view so what lies ahead of the camera is up, its box framed on its rooms as they are turned and its scale kept as the view turns, by how far apart its farthest corners are (`ExamplePlan`).

With a floor opened inside a dungeon's example, the rooms on that floor stand on the stage as they are, those below dimmed (each material's tint and glow at 30% through a property block, `Dim`; a shader taking no tint draws its part as it was) and those above put away (a room stands on a floor where its box, centred on its pivot as the game sizes it, reaches into the two metres over it, or where its own rays found ground within a metre of it, as a room's meshes can reach past its box; should no room stand on the floor opened, every room stands, so the stage is never left empty; an end cap or divider counts on a floor only by ground of its own there). An example's ground stepping down less than a storey (3 m) at a time, a cave's slope or a raised floor, is one floor, at the ground with the most room (`PlaceView.Storey`), a few milliseconds' worth of rooms changed each frame, those not on the floor passed by under the mouse, and the floor is named beside the ruler's cut, from the top as the ruler's ticks count, with how many rooms stand on it (`PlaceView.FloorLabel`). With a floor opened the plan shows only the rooms on that floor, those reaching up into the two metres over it, and the doors opening on it.

A fold in its corner puts it away, leaving a small *Plan* tab where it stood that brings it back; *Another layout*, beside the stage's other buttons, lays out a new one, and the line under them says what the example holds, or how far reading its rooms has got. The plan stands over the stage, which does not scroll, as its rooms are drawn turned (`GUIUtility.RotateAroundPivot`) and a turned drawing is not clipped to a scrolling view. A room under the mouse is lit on the plan whether the mouse is on the plan or on the stage, and a click on it goes to its entry. It is never a world's real layout, and no location ever shows where it is in a world.

The example is also built on the stage from copies of its rooms, a few milliseconds' worth a frame in the order they were placed, the entrance first (`Stage.StepExample`), each rolled like any place's copy. It stands from its generator (`DungeonExample.FromGenerator`): a camp's rooms around the location's own parts, where its generator is in it; a dungeon's rooms in place of its entrance, since the game builds them far above it, so the stage's *Inside* and *Outside* switch between the example and the entrance. Its page tells what its rooms hold, as its own prefab holds little: every part across its kinds of room, in the rows a location's page has, the loot those give right after its chests (`Knowledge.LootOf`: an item lying there, a pickable's item, what any drop table holds, such as a chest's filling), and the creatures their spawn points place before its building pieces, each with in how many of its kinds of room it is (`PlaceParts.Across`); the rooms are read as its example is laid out, or with every location. Inside, it stands on its lowest floor and opens on its top floor like a room, its floors being where its rooms' doorways are (`PlaceView.ExampleFloors`). The bundles of the kinds of room it uses are held while it is shown, since a copy needs its bundle, and let go of when the location is left or the panel closes; the kinds it does not use are let go of a frame after the stage has let go of their copies. A room under the mouse is named, found by the ray from the camera through the room boxes below the cut (`DungeonExample.Pick`), and a click that is not a drag goes to its entry.

### Names

A place goes by the name the game shows on entering it (`Teleport.m_enterText`, "Burial Chambers") or discovering it (`Location.m_discoverLabel`). Otherwise an altar goes by its boss ("The Elder's altar") and a camp by its trader ("Haldor's camp"), and anything else by its prefab name in words, without variant numbers and the makers' tags, with creatures called as the game calls them ("GoblinCamp2" is a Fuling camp). Each place says its biomes from the world's location list. A dungeon room goes by the dungeons built with its kind of room (`DungeonGenerator.m_themes` against `Room.m_theme`), so a crypt's rooms and its entrance are one place. The `in:` search looks at a place's name, not its biome.

## Links and leftovers

Besides effect lists, prefabs point at one another in many ways, and each becomes a link shown at both ends under its own heading: sounds an animation clip names, footsteps, the items a humanoid may carry, any prefab or item a field names (a projectile an attack fires, a creature's saddle, a door's key), armour sets, station upgrades, ammo, and the status effects prefabs give. A prefab the scene does not register has no entry, yet many do their work through one (a staff's projectile raising a troll); what its own fields name is linked from its user instead.

What a prefab leaves behind is paired with it: a creature's ragdoll, a tree's log and stump, a log's halves, a rock's broken version and the debris of anything destroyed. A leftover is named after its owner ("Troll · ragdoll"), takes its owner's kind so it sits beside it in the list, and links to it. One shared by many owners is named for what it is and how many leave it ("Debris of 30").

## The stage and the world

### Chips and backdrops

The stage's top right corner holds few chips: *View*, opening a box for the spin, the backdrop, the lighting and a person beside the model for size, each row switched by a click (`ScryPanel.ViewMenu`), and for a place shown its example *Inside* or *Outside* and its *Creatures*; the roof is put on and off over the ruler, and the plan folds on itself. The backdrop is plain, a sky, the grid ruled in metres, or the ground of the model's own biome, with or without the sky (`StageGround`): of the biomes it is in, the first players meet, Meadows for none.

### The biome ground

That ground is a round piece laid under the model with the world's own terrain material, each of its points coloured as the game colours its terrain to tell the biome (`Heightmap.GetBiomeColor`), nothing painted on it (`Heightmap.m_paintMaskNothing`) but the share the world keeps in the mask's fourth part, the Ashlands' lava and the Mistlands' own, here none (`StageGround.MaskShare`), a far distance for the shader to hide it by as the game gives each piece of its terrain one (`_LodHideDistance`, without which nothing draws), and for the sea's floor water over it (`_WaterLevel`), so the terrain's shader paints it as it paints the world, with the bumps it raises from each biome's own ground; it lies five centimetres under the floor, as high as those bumps rise, under the model whatever the camera does, several times as wide as what is framed and with the sky twenty times, out toward a horizon, its edge fading into the backdrop's colour or the sky's horizon under a sheet clear in its middle (`StageGround.Across`, `StageGround.Fade`).

A place paints its paths, dirt and paving on it as the game paints its terrain under it: its terrain modifiers are read off its copy while it sleeps, as stripping takes them off, and laid on the ground's mask in their order, each blending toward its colour by one less its distance over its reach, to the tenth power, times its strength (`TerrainModifier`, `Heightmap.PaintCleared`, `StageGround.Painted`); a camp's rooms paint theirs too.

The biome's grass and small plants grow on it within forty metres, as far as the game grows them around you, scattered patch by patch as the game scatters them (`ClutterSystem.GenerateVegPatch`): each kind for the biome with the game's own dice for the patch, kept by its forest, noise, height, slope, sea depth, vegetation and cleared-ground rules, the ground taken at a height typical of the biome (`StageGround.Altitude`); the kinds the game draws many times over are drawn so for the stage's camera alone (`InstanceRenderer`, `Graphics.DrawMeshInstanced`), the rest are copies. The sea's floor has the world's water over it, its surface's mesh and material with its depth and time told as the game tells them (`WaterVolume`).

The light and sky take the colours the game's most common weather in the biome has at the lighting's time of day, Studio and Day by day, Dusk by evening, Night by night, the cave keeping its own (`EnvSetup`, `StageGround.TimeFor`), and the key light casts shadows while the ground is laid. The View box's *Ground* row picks the biome: Auto for the entry's own, or any of the game's, remembered; it lies at the place's ground, so a floor opened below that cuts it away as it cuts all else, and a dungeon's inside or a room of one keeps the plain floor (`Stage.Ground.cs`).

### What the stage keeps

The ground is an object of its own that keeps everything it makes, its piece of terrain, mask, paints, grass, water and edge, and lets go of it itself (`BiomeGround`); the stage tells it each frame whether it is wanted, of which biome and where. The creatures standing on the stage are kept the same way, which wait, which stand in which room, how high each flies and which stand above a cut (`StageCreatures`), while the stage makes each copy. The example dungeon or camp standing on the stage is kept so too, its rooms, which are dimmed, what each room's rays found and the floors they make (`StageExample`), and the cut over a floor in the model (`FloorCut`); what is left in the stage itself is its camera, lights and framing.

### The turntable

The turntable is a copy far above the world on a layer the game does not use, with its own camera rendering into a texture the panel draws and its own lights. The main camera ignores that layer, the world's directional lights (the sun, and the flash a lightning strike makes for a moment, `Thunder.DoFlash`) are kept off it while the stage is filmed (`Light.GetLights`), and fog and ambient light are set for the stage only while its camera renders. The camera frames what the copy draws, far enough off for it to fill the picture, gliding out quickly so nothing leaves the picture and back in slowly once it settles, with the floor, grid and sky reaching past it (`StageFraming`); the wheel's and a drag's limits and the picture's rays are the camera's moves (`StageCamera`). A creature stands on the bottom of its capsule, as the game stands it. The stage copy is taken down while the panel is closed.

On the stage, an effect and what a model plays are heard as if beside you, and a model's own built-in sounds are muted. While a copy stands in the world, sound comes from there instead, and the stage's copies have their sound scripts switched off, since the game lets only so many of one sound play at once (`AudioMan.RequestPlaySound`).

### In the world

A model shown in the world stands where you were looking, facing you. Effects play there or on you. Projectiles are flown with the prefab's gravity and a chosen speed, and a ray stops them at the first ground or building, where their hit plays. A raid comes in no waves: for as long as it lasts, each of its creatures is rolled again at its pace, one with a cap topped up to it near you, one without one more each time (`SpawnSystem.UpdateSpawnList`), which its page tells under *Keeps coming* (`RaidWords.KeepsComing`). A raid on the stage is the first roll of each of its creatures as the game rolls it (`RaidRoll`, `RaidCrowd`), as `SpawnSystem.UpdateSpawnList` does the first time a raid's spawners run with none of its creatures about: each creature is tried as often as its cap (once without one), each try at its chance; a try stops once the creatures the pass has spawned reach its cap, and a group of its size is cut only to the cap itself, so a pass can bring more than a cap and a later creature with a smaller cap may bring none. Each creature's stars are rolled up from its lowest level at the level-up chance (`SpawnSystem.Spawn`, `GetLevelUpChance`: its own chance or 10, with the world's level or enemy level-up rate). Left out is what depends on the world: the time of day, weather and world keys a creature waits for, finding ground for it, the biome's level-up multiplier and the distance from the world's centre its stars may wait for. The copies have no bodies to push each other aside as live creatures do, so each group stands in rings around a point of its own, every body (its capsule's radius) clear of the next and the group as wide as the game spreads it (`m_groupRadius`) where that is wider, and the groups' points lie in a ring far enough apart that no two groups touch (`CrowdLayout`); a line under the stage says what came, and *Roll again* rolls a new wave. A raid that brings no creature, such as a boss's fight, keeps its card.

Sounds are copies on the camera, kept while they play, so long clips such as music play to the end and can be skipped through. The game's sound script picks a clip at random a frame after the copy wakes, so to play one variant, the copy's list is narrowed to that clip first. Location music is started by the game's `MusicLocation` when you come near, so Scry starts it instead, at your music volume.

## Input

While the panel is open, `TextInput.IsVisible` answers yes. The game already stops moving, looking, attacking and opening its menu while a text box is up, and frees the cursor. The camera zoom reads the wheel regardless, so `ZInput.Internal_GetMouseScrollWheel`, through which every wheel read of the game passes, answers nothing while the panel is open. The block lasts one frame past closing, so the Escape that closed the panel does not open the game's menu.

The game asks for mouse look apart from movement (`PlayerController.TakeInput`), so holding the right mouse button outside the panel answers only that question yes and captures the cursor as in play. Walking is allowed whenever none of the panel's boxes has the keyboard, and `Player.SetControls` never receives attack, block or dodge while the panel is open. `WalkWhileOpen` and `LookWithRightMouse` turn these off.

## Files and settings

The settings are in `BepInEx/config/isimp.Scry.cfg`: the key that opens the panel (`OpenKey`), its scale, whether the search has the keyboard on opening, walking and looking while open, how long before a tip shows, how many entries *Recent* keeps, how long after entering a world the catalog is read, whether the locations are read by themselves, the model's spinning, whether a sound plays when selected, and the diagnostics: what the log tells and whether the self-test may run. Favourites and the panel's state (its place in both views, the stage's look, the list's width and which sections are folded) are kept in `BepInEx/config/isimp.Scry/`, so they go with the profile. Favourites of prefabs not in the game right now are kept.

## Game updates

Most of what Scry shows is read from the game as it runs, so new creatures, items and mods' prefabs appear without a change to Scry. Some previews and details follow the rules of the game's own methods, and a few features reach private members by name. The first time Scry reads the catalog in a world it checks all of these and writes one line to the log when all is as expected, and otherwise a line for each part that is missing (its feature is off) or changed (it may be slightly wrong).

The check covers the private members Scry reaches by name, each of its patches, the animation events the game answers, the layers falling copies land on, the effect scripts copies keep, the status effects and prefab it looks up by name, and the code of over a hundred game methods whose rules Scry follows. A method's code is compared by its shape (`IlShape`): the sequence of its steps, leaving out what they name, which the game numbers anew in every build, so only a rewritten method counts as changed. A coroutine's code is read from the state machine the compiler makes for it, the one its `IteratorStateMachine` attribute names, so two coroutines of one name are told apart. The list is `Compatibility.Watched`; a mod that rewrites one of these methods shows it as changed too.

`tools/shapes` keeps the list current. From the repository's folder, with `VALHEIM_DIR` set (or `--dll` and the path to `assembly_valheim.dll`), `dotnet run --project tools/shapes -c Release -- --check` lists only the methods that changed, with their old and new shapes, and those that are gone. `--update` writes the changed shapes into `Compatibility.cs` and leaves the missing ones to be fixed by hand. Given `Type.Method` names instead, it prints each overload's shape, for adding a method to the list.

A public member that is renamed or removed fails where it is used, so every part of Scry's work is caught on its own: each part of each prefab while reading, each step of reading, each part of an entry's details, each section of the panel and each preview. Patch bodies live in methods of their own, run through `Guard`, because Mono compiles a whole method before running it and a missing member would otherwise fail before the guard begins. A failure that means the game changed is told once as the feature it turns off. Every feature is named once, in the list `Feature` holds: the startup check's tables name what a missing part turns off from it, every guard names the feature its part belongs to beside the part's own name for the log (the compiler holds the guards to it, and a test holds each patch class to a feature in the plugin's map), and the notice names each feature off once, whether the check found it missing or a part failed later. While anything is off an amber strip under the panel's header says what in one line (`OffWords`); its *Details* stand in the list's place with why, what to do and each part that is off, and copy them with Scry's and the game's versions for a report. The strip speaks of what is off rather than of the game, since a part of Scry failing turns a feature off the same way; its cross puts it away until more goes off. Any other failure is most likely one odd prefab, usually a mod's, and costs only that prefab's part: the first of each kind is told whole, with where it came from, the rest only counted, and all of them summed up after reading.

After an update, three things tell what needs doing: building against the new assemblies fails on every public member that changed; the check's line in the log names the private members, patches and methods that changed; and the summary after reading shows anything that now fails on many prefabs. For each changed method, read its new code against the rules Scry follows from it, then run `--update`.

## Logging

The log is written one way, by kind of line: a failure through `Faults`, told once and counted for the self-test; a line Scry always writes through `Log.Report`; something about the game or the PC a player should know, such as a key already taken or no free layer for the stage, through `Log.Warn`; and what a preview did through `Log.Note`, written only with `LogPreviews` on. A standards test holds every write to the log to these. With `LogPreviews` off (the default), Scry writes only the check's line, how long reading the catalog and the locations took, what was asked for (`/scry dump`, the self-test), warnings about the game or the PC, and anything that failed. With it on, the log also tells what each effect list and clip played and whether each part was seen or heard, what each creature's animator was seen to do and its gear, what destroyed things leave and where fallen things came to rest, any frame in which Scry's own work took 20 ms or more (split by part, with about how much memory each part allocated and where a memory cleanup of the runtime ran), and every half minute how many cleanups ran and how much of the allocation was Scry's. `/scry dump` writes every renderer of the stage copy to the log, for finding out why part of a model does not show.

## Resource monitor

`ResourceMonitor` under Diagnostics, or `/scry monitor`, shows a small box at the screen's right edge, over everything and also with the panel closed (`Monitor`, `ScryPanel.Monitor.cs`). It tells Scry's own time each frame now, on average and at the most over the last ten seconds, and its share of the frames, with a graph of those ten seconds, a column for each sixth of a second at its most (`MonitorWindow`); its outer parts (update, panel, render, its own drawing as monitor) and its largest inner parts, each smoothed over a couple of seconds; what its work allocates a second and the memory cleanups that ran in it, beside all the cleanups in the last ten seconds; and what it holds, counted once a second: its catalog's entries, the bundles it has loaded, the parts drawn on its stage, its creatures and grass, whether previews stand in the world, and the textures, render textures and meshes it made and keeps, noted as they are made so they are counted without searching all of Unity's objects (`Kept`), with the game's managed and native memory for scale. Its figures are made again four times a second. Scry measures its own work while the monitor shows, as with `LogPreviews` on, so a frame costs a little more then. For finding faults, not for play.

## Self-test

The self-test is a tool for finding faults, a plugin of its own beside Scry (`Scry.SelfTest.dll`, from `selftest/`) that a development build deploys and a release never packages; it reaches Scry's insides through `InternalsVisibleTo` and plugs in as it loads (`SelfTestHost`), and without it `/scry selftest` says it is not installed. It runs only with the `SelfTest` setting on (under Diagnostics, off by default). `/scry selftest` then tries Scry out in the world it is in and writes what it found to `BepInEx/Scry-selftest.log`, appended so earlier runs stay; with the file `BepInEx/Scry-selftest.run` present it starts by itself a few seconds after the catalog is read, once per world, and `/scry selftest stop` stops it. It uses the panel as a player would, through the same paths, in some hundred parts, run in the order `SelfTest.Scenarios` lists them and written in files named for what they test (`SelfTest.Search`, `SelfTest.Panel`, `SelfTest.Stage`, `SelfTest.Details`, `SelfTest.Mods`, `SelfTest.Previews`, `SelfTest.Raids`, `SelfTest.Locations`, `SelfTest.Layouts`, `SelfTest.Sweeps`).

The first parts check the startup check, the catalog and which locations and raids count as the game's own, and the catalog's soundness (every key once, every entry named and in a group, the tabs' counts adding up to all). They search by name, kind and biome and with each kind of search term, time the slowest search against 50 ms, keep favourites, *Recent* and the history, list every tab group by group, move with the arrow keys, filter by *Game* and *Mods*, see a tab with nothing for the search show every kind's matches, open the search's help, go round a page by the line of its sections, draw both views and search from `/scry`, and see the panel's own strip name the part running.

Then one entry of each kind goes on the stage and has its details read, and the details of creatures (weak spots, when they turn on you, how far they chase, what stars add), a piece (support and wear), items (what they are used for and where they are made), a workbench (what is made at it and built near it), a smelter, a bed, build tools and their pieces leading to each other (every tool, mods' too), the mods hooking into drops, loot and spawning with every hook looked at, the mod report written out whole and every mod station's pieces and recipes as the game names them checked against what Scry links, the report opened in the panel, the hooks watching deaths' loot in place and what was seen so far told on its creature and items, every mod loaded having a page that tells what it adds, a spawner and its creatures, and the odds items tell. The stage's lighting, backdrops and views are drawn, a bigger size makes a bigger copy, a creature stands with stars and in each of its looks, a slower animation slows its animator, a piece stands in every state of wear, the loudness follows its slider, and a new selection starts every adjustment afresh. A spread of every kind stands on the stage; selecting a different entry every frame leaves the last one shown, and after many others the stage holds no more than before (`Stage.Held`).

The previews come next: an attack, a clip played, paused, sought, looped and stopped, a sound played, stopped, paused and sought and in the variant chosen, an effect looped until stopped, an effect and a status effect on you, an item worn by the person and taken off, a tree felled whose debris goes again (`Stage.PlayedCount`), a copy standing in the world and a projectile fired, and *Clear world* taking them away. Closing the panel quiets it and opening it again brings the selection back. It follows every raid to what it brings and a raid to its creature and back by the creature's own line, sees the bosses' fights grouped apart from the raids in the order the bosses are fought and linked to their bosses both ways, stands a raid on the stage as the first roll of its creatures with every creature rolled there, rolls it again eight times, and stands every raid that brings creatures.

With the locations it loads one, sees the stage frame its entrance on its own ground, and rolls it again, reads a runestone location's texts and sees them drawn, switches between locations while they load and closes the panel on one, reads a dungeon room and sees it stand on its lowest doorway, cut open over its top floor, stepping down a floor at a time to the lowest and up to the roof, the roof button taking the roof off again, the cut moving with Shift and the wheel, starting afresh when the room is left and come back to, a location keeping its roof until the chip takes it off, and the cut set anywhere as the ruler sets it; it sees a spread of places, and the towers and caves among them, each with floors found from the top down and cut over each, no collider left on a copy, and the ruler drawn. It lays each biome's ground with the Ground backdrop, notes the colour of the ground before the model for each and saves a picture of the stage beside the log, and sees a dungeon room keep the plain floor. It sees a dungeon's stage show three chips at the most with the roof over its ruler, and its plan fold to a tab. It opens a tall dungeon's example on a floor and sees the camera look at that floor with every room on it in the picture, and at the next a floor down, the wheel zoom toward what is under the pointer and a drag keep what was grabbed under it, with a floor opened and with the roof on; it cuts through a place's tallest creature and sees what of it is above the cut still drawn, the picture there changing as the creatures are put away. It lays out a dungeon and a camp, sees each page tell what its rooms hold and the dungeon's the loot in them, and sees each built on the stage room by room (the dungeon inside, opened on its top floor and stepped down floor by floor, a room found under the mouse, and its entrance outside; the camp around the location), sees its plan draw in the stage's corner (`ScryPanel.Drawn`), follows a room and a vegvisir to their entries and back, and checks the placement rows.

Last it reads every location while one stands on the stage, which must keep its looks as bundles are loaded and let go of around it, lays out every dungeon and camp, sees every dungeon head its group with its rooms under it, stands a spread of locations and of rooms on the stage, reads every entry's details with every chip leading somewhere, noting the names of entries told as text with no chip for them anywhere on the page (`NamesInText`: whole words, the first capitalised, the longest name at a place), sees the places items are found in go to their locations, plays a place's music as Enter does with the game's music muted meanwhile and given back after, plays every location's own music, sees every boss tell its altar and every trader what it sells, sees every runestone's texts and titles in words, and sees that closing the panel lets go of every bundle.

The frame figures leave out the self-test's own checks, which run inside Scry's update (reading every entry's details at once is no player's frame): its tick is timed as a part of its own, less the parts timed inside it, so Scry's work it calls, such as a copy made, still counts (`Timing.Own`, `FrameTimes.TotalWithout`); the most its own checks took in a frame is noted. Each part also fails when any part of Scry failed while it ran (`Faults.Count`) or a feature went off for a game change, and a part of a single prefab left out (`Faults.Skipped`) fails it too, except in the parts that read mods' locations and rooms as well, where it is only noted; each tells how long Scry's own work took in its frames (`Timing.Measuring`, `FrameStats`) and how long the part took, and the run ends with the whole run's figures, its slowest frames and its length. A part that runs out of time is ended with a cleanup that puts back what it changed, so the next starts as it expects.

While it runs, a strip under the panel's header says which part runs, how far the test has got (`ScenarioRunner.Done`, `Total`, `Current`, `FailedSoFar`) and how many failed so far, with a bar and a *Stop* button; the chat says at the start how many parts there are and how to stop it. When it ends, the strip gives its headline, and its *Details* stand in the list's place: every failed part with the checks that failed in it, every skipped part with why, how many passed, and what to do next, with *Copy summary* (`SelfTestWords`). The chat gives the headline too, and the log ends with the same summary, and begins with a key to its lines.

The scenarios run one after another on the game's clock (`ScenarioRunner`, tested on a made-up clock): a failed check, an exception or a scenario that never finishes fails that one only, and its cleanup always runs. Nothing is spawned; a scenario that would stand a copy in the world or fire one skips when something of the player's is already there. When it ends the explorer is put back whole (`Explorer.Keep` and `Restore`: search, filters, selection, recent entries and history), the previews it played are stopped, the plan's section is folded again if it was, and the panel closes again if it was closed. The locations it read stay read, as *Read all locations* leaves them. Adjustments on the entry selected before are back at their defaults, as on selecting any entry.

## Limits

A mod prefab whose look is built by its own scripts may preview bare. A dungeon location's own copy leaves out its interior, which the game builds with the zone, and its rooms stand on the stage only as an example laid out by Scry, and a location's pieces show whole where the game may wear them at random when it builds the zone. The stage is lit by its own lights, so materials that depend on the world's lighting can look different there. A few things stand in for what the game does with a target and are approximations: where a swing's hit lands, an attack with no strike marked in its clips, steps heard where a foot comes down, one projectile thrown for a burst, and clips paired only by their names.

## Building

The project builds with the .NET SDK against the game's assemblies. Set `VALHEIM_DIR` to the game folder if it is not a standard Steam install, then run `dotnet build`, which also copies the DLL into the local Gale profile (`-p:DeployDir=<folder>` puts it elsewhere); `dotnet build selftest` builds and copies the self-test beside it, building Scry first. Both build against the same references (`GameReferences.props`). `dotnet test tests/Scry.Tests` runs the tests for everything in `src/Model`.
